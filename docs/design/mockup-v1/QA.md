# 인수·회귀·출시 검수

상태 표기는 `PASS / FAIL / BLOCKED / NOT RUN`. 이 문서는 **앞으로 수행할 검사**다. 기존 목업의 Chromium 캡처 통과 기록은 새 본편 구현의 검사 결과를 대신하지 않는다.

## 1. 실제 본편 명령

현재 CI는 Node.js 22, pnpm 10과 lockfile을 사용한다. 작업 환경에 이미 맞는 도구가 있으면 재설치할 필요 없다.

```bash
pnpm install --frozen-lockfile
pnpm test
node scripts/zone-report.js 10
pnpm run build
pnpm run check:dist
```

위 스모크는 현재 `.github/workflows/pr-verify.yml`의 필수 범위다. `report:growth`, `report:v9` 등의 추가 report는 관련 계약 변경 또는 저장소 최신 규칙이 요구할 때 실행한다. 존재하지 않는 “브라우저 스모크 스크립트”를 있다고 기록하지 않는다.

컴포넌트 작업 중에는 해당 새 회귀와 관련 기존 테스트를 우선 실행한다. 통합 후보에서 전체 테스트·스모크·빌드를 한 번 완료한다. 이후 변경이 없다면 동일 검사를 이유 없이 반복하지 않는다.

관련 기존 테스트 예시: `ballpark-battle.test.jsx`, `one-action-battle.test.jsx`, `portrait-only.test.js`, `v10-landscape-layout.test.js`, `v15-landscape-battleboard.test.js`, `battle-inspector.test.jsx`, `v10-card-energy-ui.test.jsx`, 공개 정보·forecast 관련 테스트. 실제 최신 main의 파일명을 C00에서 확인한다.

세로 전용 정책을 의도적으로 변경하는 테스트는 근거와 새 경로/기존 경로 계약을 함께 갱신한다. 기대값 삭제·skip·스냅샷 일괄 수락으로 회귀를 감추지 않는다.

실제 브라우저 확인은 `pnpm run dev -- --host 127.0.0.1 --port 5173 --strictPort` 또는 production build의 preview server를 쓴다. 별도 목업 서버 통과를 본편 통과로 적지 않는다.

## 2. 뷰포트와 필수 화면

| 크기 | 목적 |
|---|---|
| 1440×900 | PC 기준 미감·경기장 원근·마우스/키보드 |
| 932×430, 844×390 | 가로 휴대폰 기준, safe area를 포함한 실기기 대조 |
| 740×360, 667×375 | 낮은 높이·손패 스크롤·44px 입력 |
| 390×844 | 일반 세로·회전 전후 유지 |
| 320×568 | 좁은 세로·긴 문구·정보창·필수 행동 접근 |

전부에서 전투 선택/지원/준비/결과/정보창을 확인한다. 대표 크기에서 타이틀→시작팩→지도 스크롤→전투→보상→시설→다음 지도→이어하기를 실제 클릭한다. 승리/패배/강판/홈런과 첫 연습도 확인한다. QA 강제 상태는 도달 보조이며 실제 전이 확인을 대신하지 않는다.

프리뷰의 미지원 artId에서는 기존 View뿐 아니라 **기존 세로 레이아웃을 담는 패널**도 확인한다. 새 경로의 가로 허용 때문에 옛 화면이 잘리거나, 새/옛 View 전환·회전으로 App이 재생성돼 선택·phase·저장이 유실되면 실패다. 지원/미지원 상대가 이어지는 실제 경로를 한 번 이상 확인한다.

## 3. 반드시 남길 행동 계약 증거

- 같은 seed·시작팩·action sequence로 기존 UI와 새 UI의 비용/소비/카드/HP/주자/phase/아웃이 일치한다.
- 무선택→지켜보기, 공격→타격, 준비→준비 사용이 **단일 버튼**에서 작동한다. 선택 해제와 무료 기본 스윙이 발견 가능하다.
- 메인+지원과 지원 코스 대기, 에너지 부족, 준비 횟수 소진, 강화 카드, 긴 효과/조건 문구가 안전하다.
- 드래그/가로 스와이프가 카드 선택으로 오인되지 않는다. hover 없는 터치에서도 예측을 얻는다.
- 연출 중 더블탭·Enter 반복·정보창·회전·탭 복귀가 중복 판정/자동 진행을 만들지 않는다.
- 읽기 0/I/II 각각에서 기존 공개 수준을 지킨다. 준비 카드를 아직 쓰지 않았는데 정보 단계가 먼저 올라가지 않는다.
- 표시 피해의 `안타 시 / 희생타 시` 조건이 유지된다. 근접 실패 −2 등 실제 규칙을 성공 예상과 혼동시키지 않는다.
- 자동 진행 후 결과 한 줄이 남고, 다음 선택을 가리지 않으며, 기존 복기/설명창이 열린 동안 경합하지 않는다.
- 실험실의 별도 에너지·규칙·세이브를 메인 기본2에 덮어쓰지 않는다.

## 4. 저장과 프리뷰 격리

메인 `9zone-v10-run`, 방어 실험 `9zone-defense-lab-v1`, 기존 구버전 세이브 경로를 유지한다. 회귀용 저장은 별도 브라우저 context/profile에서 만든다. 사용자의 실제 저장을 삭제하거나 일괄 localStorage.clear하지 않는다.

정적인 검토 fixture는 기본적으로 메모리 상태이며 생산 세이브를 읽고 쓰지 않는다. 실제 런 이식 프리뷰는 별도 브라우저 context에서 기존 저장 함수를 그대로 검증한다. fixture와 실제 런 경로를 화면에 구별한다.

기존 저장 불러오기, 카드 선택 중 회전, 결과 후 저장, 새로고침·이어하기, 손상 저장 안내, 다른 화면으로 이동 후 복귀를 기록한다. iframe/reload 제거로 상태가 바뀌는 경우를 특히 본다.

## 5. 시각 검수

동일 크기·상태의 목업/새 본편을 나란히 비교한다. 전체 픽셀 일치 점수 하나를 합격 기준으로 쓰지 않는다.

1. 노을·크림/청록/주황·인물 대비가 유지되는가?
2. 타자/투수의 위치·스케일·방향·발·배트·공 궤적이 맞는가?
3. 에너지와 카드 비용을 가까이서 읽고 손패를 바로 조작할 수 있는가?
4. 현재 행동/메인/지원/실제 공을 색뿐 아니라 형태·문구로 구별하는가?
5. 결과 연출이 중요 숫자와 다음 판단을 덮지 않는가?

비교 시 허용 차이: 단일 행동 버튼, 읽기 0/I 표현, 본편의 실제 카드/결과, 조건을 명시한 예측 문구, 세로 재배치. 폰트가 로드되기 전 캡처나 이전 캐시 그림을 최종 증거로 쓰지 않는다.

텍스트 대비는 일반 본문 4.5:1, 큰 글자/비텍스트 핵심 경계 3:1을 목표로 실제 배경에서 측정한다. 키보드 포커스, 스크린리더 행동명, 44px 주요 터치 영역, reduced-motion, 음소거를 확인한다.

## 6. 용량·성능·배포

현재 규칙: dist 총량 **60 MiB**, 일반 PNG **600 KiB** 초과 차단(기존 예외 패턴 별도). 기준을 올려 새 원화를 억지로 통과시키지 않는다. 원본은 보존하고 기존 WebP 파생본 파이프라인으로 납품한다.

측정 장치를 먼저 기록한다: OS/브라우저/모델, 화면 크기, cold/warm cache, 네트워크 조건. 전투 첫 표시, 손패 반응, 이미지 디코드, 긴 프레임, 반복 전투 메모리 추세를 본다. 목표는 지정 중급 모바일에서 선택 반응 p95 100ms 이내, 60Hz 동작에서 반복적인 50ms 이상 정지 없음으로 시작하되 **측정 전 달성했다고 쓰지 않는다**. 실제 장치에서 판정할 수 없으면 해당 항목은 BLOCKED로 남긴다.

모든 카드/모션을 전투 첫 진입에 선로딩하지 않는다. 현재 손패·현재 배우 중심으로 로드한다. 아직 읽히지 않는 에셋을 기다리는 동안 입력/상태가 유실되지 않아야 한다. 배포 빌드의 `/9-baseball/` base path, 이미지/폰트 404, 캐시 갱신, 프리뷰 SHA 표시를 확인한다.

## 7. 소규모 테스터 인수

새 테스터 6–8명 규모의 방향성 검토를 제안한다. 표본은 매출/리텐션 예측치가 아니다. 기존 UI와 비교할 때 동일 seed/손패와 순서 교차를 사용한다.

| 질문/관찰 | 기록 |
|---|---|
| 첫 30초에 무엇을 해야 하는가? | 도움 요청, 첫 의미 있는 선택, 설명 |
| 버튼을 누르면 무엇이 일어나는가? | 무선택/공격/준비를 각각 예측 |
| 왜 이 카드를 고르는가? | 비용·범위·효과의 실제 차이 언급 |
| 왜 방금 결과가 나왔는가? | 정확/지원/근접 실패의 인과 설명 |
| 그림과 조작 중 무엇이 더 좋아졌는가? | 미감/이해/피로 항목을 분리 |

초기 목표 예: 8명 중 6명 이상이 첫 30초 행동을 이해하고, 7명 이상이 단일 버튼의 세 행동을 맞힘. 이는 계획상의 임시 통과선이며 현재 성과가 아니다. 틀린 이유를 읽고 UI를 수정한 다음 관련 항목만 재검토한다.
